# MAX bot

Стартовый каркас бота на Python 3.12: `maxo`, Tortoise ORM с SQLite,
Loguru и `python-dotenv`. Получение событий — только long polling.

## Запуск

В текущем рабочем каталоге `.venv` уже создано, зависимости установлены.
Заполните `BOT_TOKEN` в `.env` и запустите:

```bash
cd ~/Max_bot_hakaton
.venv/bin/python -m src.main
```

Запускайте модуль из корня проекта: это обеспечивает корректные импорты пакета `src`.

Для вывода справки токен не требуется, бот не запускается:

```bash
.venv/bin/python -m src.main --help
```

При активированном `.venv` доступны все три варианта:

```bash
python -m src.main -h
python -m src.main --help
python -m src.main help
```

Текст справки хранится в `HELP_TEXT` в `src/config.py`.

Для переопределения переменных при запуске используйте `--KEY=VALUE`:

```bash
python -m src.main --LOG_LEVEL=DEBUG --DATABASE_PATH=data/dev.sqlite3
python -m src.main --LOG_FILE="logs/my bot.log"
```

Для развёртывания с нуля:

```bash
cd ~/Max_bot_hakaton
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
test -f .env || cp .env.example .env
```

После заполнения `.env`: `python -m src.main`. Если для установки пакетов нужен
прокси: `proxychains4 python -m pip install -r requirements.txt`.

Токен выдаётся на [платформе MAX](https://business.max.ru/self).
Без `BOT_TOKEN` приложение завершается с понятным сообщением до подключения
к SQLite и API. При старте бот обновляет меню команд в MAX.

Остановка — `Ctrl+C` или `SIGTERM`: текущие задачи отменяются, HTTP-сессия
и соединения БД закрываются, очередь логов дописывается.

## Поведение

- `/start` и кнопка начала диалога — приветствие и сохранение профиля.
- `/help` — список команд.
- `/me` — ID, имя, username и дата первой регистрации в UTC.
- Остальной текст, включая неизвестные команды, повторяется без форматирования.
- На сообщение без текста бот просит отправить текст. Вложения не копируются.
- Сообщения ботов и сообщения без отправителя игнорируются.

Перед обработкой каждого сообщения и начала диалога middleware получает
или создаёт профиль в БД, обновляет имя и username и передаёт его
в контексте как `profile`. Обработчик может принять его параметром
`profile: User`, как это делает `/me`.
Проверка повторной доставки выполняется до обращения за профилем.
Для успешно обработанного события в памяти сохраняется отметка с TTL,
заданным в `PROCESSED_UPDATE_TTL` в `src/middleware.py`.
Повторная доставка в течение этого времени не вызывает повторный ответ.
Отметки автоматически удаляются по таймеру даже без новых событий.
После перезапуска отметки теряются; после истечения TTL то же событие
снова может быть обработано. Сообщения в MAX при этом не удаляются.

Обработчики одного пользователя выполняются последовательно под общим
`asyncio.Lock`; разные пользователи могут обрабатываться параллельно.
Отметка обработки ставится после успешного завершения обработчика.
При ошибке или отмене событие не помечается обработанным.
Если ответ уже отправлен, а обработчик завершился ошибкой до установки
отметки, повторная доставка может вызвать повторный ответ.
Старая таблица `processed_updates` в существующей БД больше не используется.

## Настройки

Скопируйте `.env.example` в `.env`, если `.env` ещё нет.
Приоритет значений: аргументы `--KEY=VALUE` → `.env` → переменные окружения
процесса → значения по умолчанию. Имена переменных чувствительны к регистру.
При повторении `--KEY=VALUE` побеждает последний аргумент. Значение может
содержать `=`; разделение происходит по первому знаку. Аргументы задают
переменные окружения процесса и не изменяют файл `.env`.
Пустые значения из команды или `.env` также перекрывают нижележащие источники;
для обязательных непустых настроек это приведёт к ошибке проверки.

| Переменная | Значение по умолчанию | Назначение |
| --- | --- | --- |
| `BOT_TOKEN` | — | Обязательный токен бота |
| `DATABASE_PATH` | `data/bot.sqlite3` | Файл SQLite |
| `LOG_FILE` | `logs/bot.log` | Файл логов |
| `LOG_LEVEL` | `INFO` | TRACE, DEBUG, INFO, SUCCESS, WARNING, ERROR, CRITICAL |

Относительные пути и путь к `.env` определяются от корня проекта.
Папки БД и логов создаются автоматически. SQLite использует WAL;
временные метки моделей хранятся в UTC. Логи пишутся в stderr и файл,
ротируются при 10 МБ и хранятся 7 дней.
`.env`, `.venv`, данные SQLite и логи исключены из Git.

## Структура

```text
src/
├── main.py            # запуск, polling и остановка
├── config.py          # настройки из .env и окружения
├── logging_setup.py   # Loguru и перехват стандартного logging
├── database.py        # подключение SQLite и создание таблиц
├── models.py          # модель User
├── middleware.py      # мьютекс пользователя и защита от повторов
├── instance.py        # запрет второго polling-процесса с тем же токеном
├── users.py           # сохранение и обновление профиля
└── handlers/
    ├── __init__.py    # сборка роутеров и общие фильтры
    ├── common.py      # /start, /help, /me, bot_started
    └── echo.py        # последний обработчик: эхо
```

Для нового сценария создайте модуль в `src/handlers/` с фабрикой роутера
и подключите его в `handlers/__init__.py` перед эхо. FSM пока отключена;
если понадобится, уберите `disable_fsm=True` в точке входа и выберите
подходящее хранилище состояний.

При старте создаются отсутствующие таблицы (`generate_schemas(safe=True)`).
Эта операция не изменяет уже существующие таблицы. После изменения моделей
нужны [миграции Tortoise ORM](https://tortoise.github.io/migration.html).

Для одного токена запускайте один процесс polling. Повторный запуск из этого
проекта на том же сервере блокируется через `flock` (Linux); при завершении
процесса блокировка освобождается автоматически. Накопленные события
не отбрасываются; webhook-подписки автоматически не удаляются.

`marker` в журнале maxo — курсор следующего запроса, общий для пачки событий,
а не ID отдельного сообщения. Курсором управляет maxo; отдельного вызова
подтверждения сообщения у MAX нет. Для поиска повторов используйте записи
`Обработка события` / `Событие обработано` / `Повтор события пропущен`
с `key`, включающим ID бота, чата и сообщения.

## Зависимости

Прямые зависимости закреплены в `requirements.txt`.
Python 3.12 выбран потому, что [maxo не поддерживает Python 3.11](https://pypi.org/project/maxo/0.10.0/).
В [Tortoise ORM](https://pypi.org/project/tortoise-orm/1.1.9/)
SQLite входит в базовую установку через `aiosqlite`; extra `[sqlite]` не нужен.
Модуль `dotenv` устанавливается пакетом `python-dotenv`.

## Docker

По умолчанию используется `python:3.12-alpine`:

```bash
docker build -t maxbot:alpine .
docker run --rm maxbot:alpine --help
```

Версия Python и вариант базового образа настраиваются:

```bash
docker build -t maxbot:slim \
  --build-arg PYTHON_VERSION=3.12 \
  --build-arg PYTHON_VARIANT=slim .
```

Для текущего maxo используйте Python 3.12–3.14.
Допустимы также варианты с версией ОС, например `alpine3.23`
или `slim-bookworm`, если такой тег существует у образа Python.

В Dockerfile три команды `RUN`:

1. Системные пакеты: автоматический выбор `apk` или `apt-get`.
2. Создание `/opt/venv` и установка `requirements.txt`.
3. Создание пользователя `app` и настройка прав.

Сборка выполняется в два этапа: компиляторы остаются в `builder`,
в итоговый образ копируются виртуальное окружение и исходники.
Пользователь приложения может писать в `data`, `logs` и свой
домашний каталог; код и библиотеки принадлежат root.

Запуск с токеном из `.env` и сохранением данных в Docker volumes:

```bash
docker run -d --name maxbot \
  --env-file .env \
  --mount type=volume,source=maxbot-data,target=/app/data \
  --mount type=volume,source=maxbot-logs,target=/app/logs \
  maxbot:alpine
```

Файл `.env` не включается в образ. `--env-file` передаёт его значения
как окружение контейнера. Для переопределения настроек добавьте
аргументы после имени образа, например `--LOG_LEVEL=DEBUG`.

```bash
docker logs -f maxbot
docker stop --timeout 30 maxbot
```

Python запускается напрямую и получает SIGTERM от Docker.
UID/GID пользователя по умолчанию — `10001:10001`; их можно
изменить аргументами сборки `APP_UID` и `APP_GID`.
При подключении папок хоста их права должны разрешать запись
выбранному UID/GID. Для общей блокировки нескольких контейнеров
с одним токеном они должны использовать общий volume `data`.

Тесты и линтеры не добавлены.
